# Internationalization

Languages: [Deutsch](../de/I18N.md) | [English](I18N.md)

## Goal

This repository should be navigable for German-speaking and international users without rewriting the existing prompt artifacts unnecessarily. German remains the domain default language, and English is the most important alternative language.

## Language Priority

For repository contents, the priority is:

1. explicit language file or language link, for example `README.en.md`
2. explicit user request in a GPT conversation
3. detectable language of the user request, if the respective GPT artifact contains that rule
4. German as the stable fallback

The repository itself has no application runtime, CLI or server process. Therefore, it has no central automatic system-locale detection. Future tools or generators should use the priority `user setting`, `project configuration`, `system locale`, `LC_ALL`/`LC_MESSAGES`/`LANG`, `German`.

## GitHub View

GitHub does not automatically switch the normal repository view based on visitor language. Internationalization is therefore organized explicitly:

```text
README.md
README.en.md
docs/
  de/
  en/
CONTRIBUTING.md
CONTRIBUTING.en.md
CHANGELOG.md
CHANGELOG.en.md
```

Every central Markdown file should contain concrete language links at the top.

## Package READMEs

Every GPT folder with an internationally relevant overview gets:

- `README.md` as the German default overview
- `README.en.md` as the English alternative overview

Domain source artifacts such as `systemprompt.md`, `fachwissen.md`, `bootloader.md` and `beispiel.*` remain German unless a complete domain-reviewed translation exists. This avoids uncontrolled meaning changes in prompt logic, security notes and domain rules.

## Product Language Packs

Every central GPT product folder additionally contains localized product components under:

```text
<GPT folder>/
  i18n/
    en/
    es/
    fr/
    pt-BR/
    it/
    nl/
    pl/
    tr/
    zh-Hans/
    ja/
```

Every language pack contains:

- `README.md`
- `customgpt_infos.md`
- `systemprompt.md`
- `bootloader.md`
- `fachwissen.md`
- `beispiel.md`

These files are localized product overlays. They do not replace the German source artifacts; they make the product components directly usable in the target language and link back to the canonical German files. This keeps prompt behavior, safety boundaries and technical IDs consistent.

The language packs are generated reproducibly with:

```powershell
python scripts/generate_product_i18n.py
python scripts/validate_repository_i18n.py
```

## UTF-8 and Unicode

All text files remain UTF-8. German umlauts are written as real characters, not ASCII transliterations. New validations also check Unicode fixtures with umlauts, accents, non-Latin characters, emojis and bidirectional text examples.

Validation sample:

```text
ä ö ü Ä Ö Ü ß é ñ 中文 العربية עברית 😀
```

## Formatting and Locale

Because the repository contains no running software, there is no central date, number or currency formatting layer. New applications or generators should use locale-aware standard functions of their stack and document German as fallback.

## Adding New Languages

For additional languages:

1. Choose a BCP 47 language code, for example `fr` or `es`.
2. Add a new documentation route under `docs/<language-code>/`.
3. Add product language packs in `scripts/generate_product_i18n.py`.
4. Add language-specific variants of central files, for example `README.fr.md`.
5. Update language links in all affected files.
6. Do not translate technical IDs, filenames, model parameters or JSON field names.
7. Extend `scripts/validate_repository_i18n.py` if the new language should become mandatory.

## Tests

The i18n structure is checked with:

```powershell
python scripts/validate_repository_i18n.py
```

The check validates required files, language links, local Markdown links, UTF-8, Unicode fixtures and the expected German default structure.
