# Internationalisierung

Sprachen: [Deutsch](I18N.md) | [English](../en/I18N.md)

## Ziel

Dieses Repository soll für deutschsprachige und internationale Nutzer verständlich navigierbar sein, ohne die bestehenden Prompt-Artefakte unnötig umzuschreiben. Deutsch bleibt die fachliche Standardsprache, Englisch ist die wichtigste Alternativsprache.

## Sprachpriorität

Für Repository-Inhalte gilt:

1. explizite Sprachdatei oder Sprachlink, zum Beispiel `README.en.md`
2. explizite Nutzeranforderung in einem GPT-Gespräch
3. erkennbare Sprache der Nutzeranfrage, sofern das jeweilige GPT-Artefakt diese Regel enthält
4. Deutsch als stabiler Fallback

Das Repository selbst hat keine Anwendungslaufzeit, keine CLI und keinen Serverprozess. Deshalb gibt es keine zentrale automatische System-Locale-Erkennung. In späteren Tools oder Generatoren soll die Priorität `Benutzereinstellung`, `Projektkonfiguration`, `System-Locale`, `LC_ALL`/`LC_MESSAGES`/`LANG`, `Deutsch` verwendet werden.

## GitHub-Ansicht

GitHub zeigt die normale Repository-Ansicht nicht automatisch abhängig von der Besuchersprache an. Die Mehrsprachigkeit wird deshalb explizit organisiert:

```text
README.md
README.en.md
docs/
  de/
  en/
CONTRIBUTING.md
CONTRIBUTING.en.md
CHANGELOG.md
CHANGELOG.en.md
```

Jede zentrale Markdown-Datei soll oben konkrete Sprachlinks enthalten.

## Paket-READMEs

Jeder GPT-Ordner mit international relevantem Überblick erhält:

- `README.md` als deutsche Standardübersicht
- `README.en.md` als englische Alternativübersicht

Die fachlichen Quellartefakte wie `systemprompt.md`, `fachwissen.md`, `bootloader.md` und `beispiel.*` bleiben deutsch, sofern keine vollständige fachlich geprüfte Übersetzung vorliegt. Das verhindert unkontrollierte Bedeutungsänderungen in Prompt-Logik, Sicherheitshinweisen und Domänenregeln.

## UTF-8 und Unicode

Alle Textdateien bleiben UTF-8. Deutsche Umlaute werden als echte Zeichen geschrieben, nicht als ASCII-Umschreibung. Neue Validierungen prüfen zusätzlich Unicode-Fixtures mit Umlauten, Akzenten, nicht-lateinischen Zeichen, Emojis und bidirektionalen Textbeispielen.

Beispiel-Zeichenfolge für Validierungen:

```text
ä ö ü Ä Ö Ü ß é ñ 中文 العربية עברית 😀
```

## Formatierung und Locale

Da das Repository keine laufende Software enthält, gibt es keine zentrale Datums-, Zahlen- oder Währungsformatierung. Neue Anwendungen oder Generatoren sollen locale-bewusste Standardfunktionen des jeweiligen Stacks verwenden und Deutsch als Fallback dokumentieren.

## Neue Sprachen ergänzen

Für weitere Sprachen:

1. Sprachcode nach BCP 47 wählen, zum Beispiel `fr` oder `es`.
2. Neue Dokumentationsroute unter `docs/<sprachcode>/` anlegen.
3. Zentrale Dateien als sprachspezifische Variante ergänzen, zum Beispiel `README.fr.md`.
4. Sprachlinks in allen betroffenen Dateien aktualisieren.
5. Technische IDs, Dateinamen, Modellparameter und JSON-Feldnamen nicht übersetzen.
6. `scripts/validate_repository_i18n.py` erweitern, wenn die neue Sprache als Pflichtsprache gelten soll.

## Tests

Die i18n-Struktur wird mit folgendem Befehl geprüft:

```powershell
python scripts/validate_repository_i18n.py
```

Der Check validiert Pflichtdateien, Sprachlinks, lokale Markdown-Links, UTF-8, Unicode-Fixtures und die erwartete deutsche Standardstruktur.
